Your Reflection Loop Is Just a Model Arguing With Itself

And the fix reveals something deeper about how agentic systems should be designed.

J.S. Dennis 2026 ~12 min read Agentic AI

There's a pattern that shows up in almost every production agentic AI system: after a model generates output, you run a reflection pass to check it. The model critiques its own work, revises, and returns something better.

This is good practice. It genuinely improves output quality. The problem is how almost everyone implements it: they use the same model — often with nearly the same prompt — to do both jobs.

That's not reflection. That's a model agreeing with itself.

The Hidden Assumption in Self-Reflection

When a model generates an answer, it doesn't just produce text — it commits to a set of implicit assumptions. Framing choices. Scope decisions. Things it treated as not worth questioning. The output is downstream of those assumptions.

When you ask the same model to critique that output, it starts from the same prior. It will catch surface errors — factual mistakes, logical gaps it can now see with fresh attention. But it is structurally unlikely to surface the assumptions it already committed to. It doesn't know what it doesn't know, and a reflection pass doesn't fix that.

The point isn't that the reviewer is smarter. It's that they come in without your priors.

This is the same reason peer review works better than self-review in science. The fix is obvious once you name it: your critic and your generator should be architecturally independent. At minimum, a separate system prompt with genuinely different instructions. In high-stakes applications, a different model entirely — ideally from a different vendor, trained on different data, with different RLHF biases.

A fast, cheap, different model as a critic is often more valuable than a slow, expensive same-model reflection loop. Not because it's better at reasoning. Because it's differently wrong.

The Deeper Problem: Patterns Without a Framework

Once you start pulling on this thread, a bigger issue surfaces.

The agentic AI space has catalogued a large set of design patterns — prompt chaining, routing, parallelization, planning, multi-agent collaboration, RAG, human-in-the-loop, memory management, exception handling, and more. The literature lists 21 of them. What's missing is a unifying framework that treats them as configurations of the same underlying system rather than distinct architectural choices you pick between.

That's the gap this post tries to fill.

The Agent Execution Mesh

Every agentic pattern, when you look closely, is a specific configuration of three primitive components:

1. A unit of work — a task, prompt, or tool call with defined inputs and a goal
2. A dispatch decision — how that work gets executed (which model, which pattern, serial vs. parallel)
3. A quality gate — a check on the output before it proceeds

These three primitives don't change across patterns. What changes is how they're configured.

Model Diversity as a First-Class Design Dimension

Now we can revisit the reflection problem with cleaner vocabulary. The quality gate layer is where model selection actually matters most — and not just for cost. There are two meaningful axes:

← Same Architecture Different Architecture →
High Cap · Same
  • Planning
  • Multi-step reasoning
  • Deep reflection
★ High Cap · Different
  • Adversarial review
  • Assumption stress-test
  • Cross-vendor critique
Low Cap · Same
  • Routing
  • Extraction
  • Classification
★ Low Cap · Different
  • Fast validation
  • Cheap critique
  • Grounding check

The two highlighted quadrants on the right are underused. A small model from a different vendor critiquing a frontier model's output — not because it's smarter, but because it comes from a different training distribution — surfaces error classes that same-model reflection systematically misses.

This isn't theoretical. A 2025 paper analyzing LLM agent system prompts found that multi-model evaluation discovers categorically different vulnerability classes than single-model analysis. The cross-vendor adversarial review cost $0.27 in API calls.

What This Looks Like in Practice

The framework suggests clean separation between the three layers. The essential structure:

pseudocode — gate registry pattern
class GateRegistry:
    configs = {
        "fast_validate": GateConfig(
            model=ModelSpec(capability="cheap", independence="different"),
            pattern="binary",
        ),
        "adversarial_review": GateConfig(
            model=ModelSpec(capability="mid", independence="cross-vendor"),
            pattern="critique_then_score",
            focus="assumption_violations",  # not grammar — hidden assumptions
        ),
        "deep_reflection": GateConfig(
            model=ModelSpec(capability="frontier", independence="same-family"),
            pattern="chain_of_thought",
            focus="logical_consistency",
        ),
        "human_gate": GateConfig(
            trigger="irreversible_action OR confidence < 0.7",
        ),
    }

def execute(task: TaskEnvelope, dispatch: DispatchConfig) → Result:
    # Dispatch: plan and fan out workers
    outputs = run_workers(dispatch(task, dispatch))

    # Gate: select based on task type and stakes
    gate = GateRegistry.get(task.gate_config)
    verdict = gate.evaluate(outputs)

    if verdict == "PASS":
        memory_bus.write(task, outputs)
        return outputs
    elif verdict == "REVISE":
        return execute(task.with_feedback(verdict.notes), dispatch)
    elif verdict == "ESCALATE":
        return human_queue.submit(task, outputs)

Three design principles enforced by this structure: model names never appear in business logic (only capability and independence specs); gate configs are declarative and stored separately from execution; and the same execute() function handles all patterns — only the configs change.

Where This Breaks Down

01
Multi-system / A2A boundaries Once agents don't share a runtime, the unified dispatch and gate layers become a distributed systems problem. MCP and A2A protocol exist at this boundary, and the internal framework has to treat them as black boxes. The mesh handles everything inside one orchestrator cleanly; cross-system coordination is a different problem.
02
Gate config selection is still manual The framework provides the slots; it doesn't tell you which gate config to use for a given task. When to apply adversarial review vs. fast validation vs. human gate still requires explicit design decisions. Automating that selection is an open problem.
03
Cross-vendor latency costs are real Adversarial review with a different model adds a round-trip. The $0.27 example is cost, not latency. For latency-sensitive applications, the independence benefit has to be weighed explicitly against time cost.
Summary
  • Self-reflection loops using the same model as generator and critic are structurally limited — the critic inherits the generator's priors
  • Model diversity at the quality gate is a first-class design dimension, not an optimization afterthought
  • All major agentic design patterns are configurations of the same three-primitive mesh: task envelope, dispatch layer, quality gate
  • Treating them as configurations rather than distinct architectures makes systems easier to reason about, test, and extend
  • The underused pattern: fast + cheap + architecturally different as a critic surfaces error classes same-model reflection misses
